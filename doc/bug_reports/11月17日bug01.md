## 二、详细发现

### BUG-01 [P1] 左右同类修饰键同时使用时发生释放误判

**位置**：`crates/macos-adapter/src/lib.rs:673-719`，特别是 `modifier_for_key_code()`；关联 `crates/rule-engine/src/lib.rs:349-355、501-504、607-616`。

**触发步骤**：启用映射后，按住左 Option，再按住右 Option，先松开左 Option，最后松开右 Option。同类的 Shift、Control、Command 判断也使用左右共用标志。

**实际结果与原因**：左 Option 松开时，右 Option 仍然使 Option 汇总标志保持置位。函数把左 Option 的释放归一化为左 Option 仍按下，引擎再次处理 Down。两侧全部松开后，左 Option 的物理/逻辑状态仍残留，可能造成后续输入携带错误修饰状态。

**验证证据**：通过 `CGEventCreateKeyboardEvent` 和 `CGEventSetFlags` 构造四个 `flagsChanged` 对象，再交给真实 normalizer 和引擎：

```text
keycode/flags: 58/0x80020 → 61/0x80060 → 58/0x80040 → 61/0
第三步输出：Key(58), phase: Down
最终状态：physical_down(Key58)=true
全部物理键已松开后，release_all() 仍输出 Key58 Up
```

这是事件对象与引擎复现，未执行全局事件注入。应使用左右独立的设备标志，或可靠地维护每一侧的物理状态，并增加双侧同时按住、不同释放顺序的测试。

### BUG-02 [P1] 输入源错误和权限拒绝路径未清理按键绑定

**位置**：`src-tauri/src/lib.rs:413-422、456-470`；对照正常停用路径 `374-381` 和注入失败路径 `507-514`。

**触发条件**：某映射目标已经收到 Down，但尚未收到 Up；此时输入源后台服务报告异步错误，或用户重新检查权限后得到拒绝结果。

**实际结果与原因**：前者直接切到 `Degraded` 并返回 Pass；后者仅停止 adapter、切到 `PermissionRequired`。两条路径均不调用 `engine.release_all()`。后续原始键的 Up 因状态不再是 Running 而直接透传，映射目标的 Up 无法生成。例如 A→B 已输出 B Down，降级后 A Up 透传，B 的逻辑按下状态一直残留。

**验证性质**：静态调用链确认，未撤销用户真实权限，也未制造输入源系统故障。即使权限已不足以成功补发释放，也应统一清空/记录残留状态，尝试安全释放，并提供恢复策略；不能跳过已有的安全停用流程。

### BUG-03 [P1] 合法配置可触发平台不支持的输出，令整个运行时降级

**位置**：`crates/config/src/lib.rs:277-289、299-323、365-374`；`crates/macos-adapter/src/lib.rs:787-788、835-840`；`src-tauri/src/lib.rs:501-514`。

**触发示例**：导入或新增以下任一规则，再启用并触发：

```text
scroll:vertical → invert_scroll
key:11 → mouse:right
key:11 → shortcut:lock_screen
```

**实际结果与原因**：配置编译接受鼠标输出、滚轮反转，以及 `lock_screen`、`show_desktop`、`close_window` 系统动作；但平台分别返回 `Unavailable` 或 `InvalidEvent`。运行时因此进入 `Degraded`，后续所有常规映射停止，影响超出该条规则。

**验证性质**：已沿配置解析、引擎输出、平台错误返回、运行时降级的分支静态核实；没有实际触发系统锁屏或鼠标注入。`SwitchInputSource`、`TogglePinyinEnglish` 和 `ShowClipboard` 有上层专门分派，不属于本项所称的未实现系统动作。

**建议**：实现相应的平台输出，或在配置编译阶段明确拒绝尚不支持的动作，避免“导入成功，首次使用后整个映射停止”。

### BUG-04 [P2] 配置存储代码未接入应用，重启恢复默认值

**位置**：`src-tauri/src/lib.rs:624-629、808-819、847-877、1014-1029`；已有存储函数位于 `crates/config/src/lib.rs:510-541`。

**复现步骤**：新增一条规则、导入自定义配置或切换预设，确认本会话生效，然后退出并重新打开应用。

**实际结果与原因**：启动入口固定使用 `AppConfig::default()`；新增、导入和预设切换仅修改内存。项目虽实现 `load()`/`save_atomic()`，生产启动和配置变更路径都没有调用它们，也没有接入本地 `config.toml` 的位置。会话中的配置修改不能自动恢复。

**验证性质**：静态确认。手动导出的 TOML 文件不会因此丢失，但每次启动都需重新导入；这与设计文档的本地配置恢复要求不符。建议接入启动加载、验证失败回退、变更后的原子保存，并明确区分“导出副本”与“保存当前配置”。

### BUG-05 [P2] 普通键盘事件丢失修饰键左右侧信息

**位置**：`crates/macos-adapter/src/lib.rs:656-668`。

**触发步骤**：按右 Control+C，或配置一条 `chord:right_control+key:11` 规则后用右 Control+B 触发。

**实际结果与原因**：`modifiers_from_flags()` 将 Shift、Control、Option、Command 汇总标志全部转换为 `LEFT_*`。右侧组合会误命中左侧规则，要求右侧修饰键的普通组合规则则无法正确匹配。

**验证证据**：给 Key8 Down 设置右 Control 标志 `0x42000`，真实 normalizer 输出 `ModifierSet(4)=LEFT_CONTROL`，而 `RIGHT_CONTROL` 是 `ModifierSet(8)`；默认规则随后输出 Command+C。需要在普通字符事件中保留侧别，而不仅在 `flagsChanged` 中区分。

### BUG-06 [P2] 目标键同时由映射和原生按键持有时被提前释放

**位置**：`crates/rule-engine/src/lib.rs:494、534-550、554-575`。

**复现步骤**：配置 A(`key:0`)→S(`key:1`)；依次 A↓、物理 S↓、A↑，此时物理 S 仍按着。

**实际结果与证据**：

```text
A↓ → Emit(S Down)
S↓ → Pass
A↑ → Emit(S Up)，但 physical_down(Key1)=true
```

**原因**：目标键引用计数仅登记映射输出，透传来源不参与计数。释放 A 时计数归零，导致目标应用收到过早的 S Up。现有共享目标测试只覆盖两个映射来源。

**建议**：统一跟踪透传与映射来源对同一逻辑键的持有关系，并覆盖两种按下顺序及两种释放顺序。

### BUG-07 [P2] modifier_chord 的 pass/suppress 被错误执行为切换输入源

**位置**：`crates/rule-engine/src/lib.rs:434-449`；配置允许这两个动作的位置为 `crates/config/src/lib.rs:299-305`。

**复现步骤**：创建纯修饰键规则 `modifier_chord:left_control|left_shift`，分别配置 `pass` 和 `suppress`；按下 Ctrl、Shift，再松开 Shift。

**实际结果**：两种配置均输出 `SystemShortcut(SwitchInputSource)`。

**原因与建议**：执行分支只处理 `Action::Replace`，其他动作全部回退为切换输入源。应完整执行规则声明的动作；若某动作不支持这种触发器，应在编译阶段报错，不能替换成另一个动作。已通过真实 Rust 引擎分别复现两种情况。

### BUG-08 [P2] 纯修饰键规则不检查应用作用范围

**位置**：`crates/rule-engine/src/lib.rs:152-161、425-449`；普通规则匹配对照 `145-149`。

**复现步骤**：建立仅限 `com.example.Editor` 的 Ctrl+Shift 规则；把输入事件的应用上下文设为 `com.apple.finder`；依次 Ctrl↓、Shift↓、Shift↑。

**实际结果与原因**：引擎仍输出该规则的动作。`find_modifier_chord()` 只比较修饰键集合和 Up 阶段，遗漏了普通 `find()` 中的 `scope_matches()`。

**验证边界**：本项在引擎层已复现。当前原生适配将 `app_context` 固定为 None，前台应用接入仍未完成；这不改变纯修饰键分支绕过 scope 的事实。若应用范围暂不支持，应拒绝相应配置，避免将受限规则变成全局规则。复现仅检查输出模型，没有执行系统动作。

### BUG-09 [P2] 规则开关仅改变前端布尔值

**位置**：`ui/app.js:25-35`。

**复现步骤**：在设置页关闭“左 Option → Windows”或一条已新增的自定义规则，然后继续使用该映射；也可导出配置查看规则的 enabled 值。

**实际结果与原因**：点击处理器仅翻转 `state.rules[index].enabled` 并重新渲染，没有任何后端调用。后端运行规则和导出配置均不受影响，界面显示“已关”但映射继续执行。

**验证证据**：Node VM 加载真实 `app.js`，注入模拟 Tauri bridge，点击首个规则开关；本地 enabled 变为 false，而后端调用次数为 0。

**建议**：给每条显示规则关联稳定的后端标识，通过命令更新配置、编译并应用，成功后再更新界面；失败时回滚开关。

### BUG-10 [P2] 多修饰键录制语法无法被后端解析

**位置**：`ui/rule-editor-core.js:48-54`；`crates/config/src/lib.rs:269-274、338-351`。

**复现步骤**：点击“录制按键”，录制 Ctrl+Shift+B，设置一个合法输出动作并提交。

**实际结果与证据**：前端将多个修饰键用 `+` 连接，而后端只接受修饰键之间用 `|`，再用 `+` 分隔主键：

```text
录制输出：chord:left_control+left_shift+key:11
后端编译：Err(InvalidRule("keyboard_rules[0].trigger"))
有效语法：chord:left_control|left_shift+key:11
后端编译：Ok(1)
```

单修饰键录制测试不会暴露此问题。建议统一语法，并增加“真实录制结果提交给配置编译器”的交叉验证。

### BUG-11 [P2] 添加首条自定义规则会意外撤掉回退的默认快捷键

**位置**：`crates/config/src/lib.rs:175-199、480-494`；新增规则入口 `src-tauri/src/lib.rs:595-610`。

**复现步骤**：默认配置切到 `custom`，使用 Ctrl+C 等默认快捷键；新增第一条无关自定义规则，例如 `key:12 → key:13`；再使用 Ctrl+C。

**实际结果与证据**：空 custom 预设编译出 13 条顶层默认规则；只添加一条自定义规则后，编译结果变成 1 条，先前回退的 Ctrl+C、Ctrl+F5 等显式规则消失。`shortcut` 空预设同样存在这个边界行为。

**原因与建议**：回退条件是整个 profile 的所有规则列表为空，首条规则会关闭整套回退。应明确预设是独立集合还是继承默认集合，并使用一致的合并/初始化方式，避免添加规则带来无关行为变化。这里的“默认快捷键消失”指显式规则；引擎中的内建修饰键转换仍可能生效。

### BUG-12 [P2] 规则列表与预设选择未反映真实配置

**位置**：`ui/app.js:1-15、78-80、186-204`；后端状态已返回 profile：`src-tauri/src/lib.rs:793-795`。

**复现步骤**：导入当前 profile 为 custom、且包含不同规则的配置，或先新增规则再刷新设置页。

**实际结果与原因**：列表重新显示写死的 9 行默认规则，新增/导入规则无法完整反映到界面。`syncRuntime()` 不读取规则，也忽略后端返回的 `view.profile`，下拉框可能仍显示 Windows 物理键位。切换预设后也没有重载规则列表。

**验证证据**：模拟后端返回 `profile=custom`，实际 `app.js` 同步完成后，下拉框仍为 `windows_physical`，规则列表仍为硬编码 9 行。

**建议**：加载实际活动配置作为唯一规则数据源，并在启动、导入、切换预设及配置变更后刷新界面。显示层不应维护与后端无关联的规则副本。

### BUG-13 [P2] 从降级状态启用成功后仍显示“已降级”

**位置**：`ui/app.js:37-50、65-75`。

**复现步骤**：刷新到 `runtimeStatus=Degraded` 的状态；修复故障后点击 Windows 模式开关，后端启用成功并返回 true。

**实际结果与原因**：处理器只修改 `state.enabled`，没有同步 `state.runtimeStatus`。`renderStatus()` 仍优先按旧的 Degraded 渲染，出现开关“已启用”、标题“Windows 模式已降级”的矛盾状态；需要手动刷新才恢复。

**验证证据**：Node VM 中将状态设为 Degraded，模拟 `toggle_mode` 成功返回 true，真实处理器执行后 enabled 为 true，标题仍是“Windows 模式已降级”。建议模式切换后重新查询完整运行状态，并同步托盘操作造成的变更。

### BUG-14 [P2] 剪贴板保存失败后，打开面板会丢弃未落盘记录

**位置**：`src-tauri/src/clipboard.rs:389-395、423-426、459、595-600`；关联 `crates/macos-adapter/src/clipboard.rs:101-103`。

**复现步骤**：先成功记录 alpha；暂时令历史目录不可写，复制 beta；保存失败后内存仍包含 beta；恢复目录写权限，再打开面板或刷新历史。

**实际结果与原因**：采集先更新内存，保存失败没有回滚或标记待保存状态；Show/Refresh 却无条件从旧文件覆盖 `history` 和 `core.history`，beta 因此消失。Show 在第 426 行还可能清掉之前的保存错误提示。由于剪贴板 changeCount 已消费，原记录不会因下次轮询自动重新入库。

**验证证据**：使用真实 `clipboard_core` 保存和加载接口，隔离目录权限模拟保存失败，得到：

```text
save_failed=true, memory_entries_before_reload=2
entries_after_reload=1, beta_survives=false
```

该实测覆盖存储层，worker 的覆盖和清错行为由调用链确认。建议保留 dirty 内存并重试保存；界面快照刷新读取 worker 当前状态，外部文件重载另设明确入口。

### BUG-15 [P2] 剪贴板面板的 Enter 覆盖了当前聚焦按钮

**位置**：`ui/clipboard.js:144-154`；相关按钮处理 `94-100、135-143`。

**复现步骤**：打开历史面板，按方向键高亮一条记录，Tab 到“清空历史”“删除”或关闭按钮，再按 Enter。

**实际结果与原因**：文档级处理器不检查 `event.target`，直接阻止 Enter 默认行为并选择当前高亮记录。结果是执行粘贴，而不是激活聚焦按钮。

**验证证据**：Node VM 运行真实 `clipboard.js`，将 Enter 的 target 设为 `clipboard-clear`，观察到 `preventDefault=true`、调用 `select_clipboard_item(1)`，没有调用 `clear_clipboard_history`。

**建议**：列表快捷键只在列表导航上下文生效，或跳过按钮、链接、输入控件等独立交互元素。

### BUG-16 [P2] 正常退出没有尝试释放已注入的按键

**位置**：`src-tauri/src/lib.rs:698、706-725`；已有 Shutdown 分支位于 `425-432`。

**触发条件**：某个映射键已经发出 Down、尚未发出 Up，此时从托盘退出应用。

**实际结果与原因**：托盘直接 `app.exit(0)`，RunEvent 回调没有处理退出清理；`RuntimeCommand::Shutdown` 在生产退出路径未被调用，因此不会尝试补发已有逻辑键的释放。

**验证性质**：静态确认缺少退出清理，不声称已在真实目标应用观察到卡键。建议在退出生命周期调用 Shutdown、发送释放输出并结束事件服务，覆盖“按住映射键退出”的真机回归。
